# Модель оценки риска

Версия: 2026-09-24. Формула реализована в `backend/app/analysis.py`; пороги сохраняются через `/api/config`.

| Severity правила | Балл finding | Диапазон Risk Score по умолчанию |
|---|---:|---:|
| Low | 5 | 10–29 |
| Medium | 10 | 30–59 |
| High | 25 | 60–79 |
| Critical | 40 | 80–100 |

Для объекта без находок Score = 0. Иначе `base` — нижняя граница диапазона самой высокой severity. `Score = min(верхняя граница, base + round(0.3 × сумма баллов остальных находок))`. Приоритет severity позволяет сохранять смысл уровней: несколько Medium правил не становятся Critical сами по себе. Конфиг требует `10 ≤ Medium < High < Critical ≤ 100`. Пользователь, сервисный аккаунт и компьютер получают score независимо. Тип объекта учитывается через применимость правил и их severity: сервисный бессрочный пароль, привилегии или интерактивные права; компьютерная неактивность и делегация. Путь к Tier 0 (`Domain Admins`, `Enterprise Admins`, `Schema Admins`, `Administrators`) имеет Critical; делегированная test OU имеет High. Finding об аутентификации также связан с целевым пользователем и участвует в его score только при наличии прочитанных событий.

Доменная политика получает отдельный Score: сумма баллов своих правил, не выше 100. Слабая FGPP получает отдельную находку; её применённость к аккаунту определяется по `msDS-ResultantPSO`, а не по одной только ссылке применения. Общий `AD Security Score = max(0, 100 − округлённое среднее Risk Score пользователей, компьютеров и доменной политики)`. Политика включается, когда её удалось прочитать. 100 означает отсутствие находок в оценённых источниках, **не** доказательство отсутствия риска в недоступных источниках.

`lastLogonTimestamp` приблизителен. Неактивный новый аккаунт без наблюдаемого входа не создаёт finding, пока его возраст не достигнет порога. Доказательство времени входа не включает все DC, если их несколько. Отсутствие старого пароля или SIDHistory в текущем lab снимке не доказывает, что соответствующее правило работает на положительном live случае: это отдельно проверено unit-тестами. Источник Event Log без доступа обозначается `not_evaluated`; нулевое число событий не следует трактовать как ноль атак.

# Identity Risk Radar

Локальное приложение для анализа рисков Active Directory. React показывает результаты сканирования, FastAPI собирает данные, проверяет правила, рассчитывает риск и отдаёт CSV-отчёт. Сразу после запуска доступен демонстрационный источник; после готовности Windows Server можно переключиться на LDAP.

## Архитектура

```text
React (5173)
  │ HTTP /api
  ▼
FastAPI (8000)
  ├── Demo Collector ── data/demo_ad_data.json
  └── LDAP Collector ── Active Directory (389/636)
          │
          ▼
  Общая модель Account / Group / Snapshot
          │
          ▼
  Анализ вложенных групп → правила риска → Risk Score
          │
          ▼
  SQLite: снимки сканирования → API / Dashboard / CSV
```

Frontend никогда не соединяется с Active Directory напрямую. Пароль учётной записи сканера вводится в скрытое поле интерфейса, передаётся backend для подключения и не записывается в `.env` или SQLite. Сканирование только читает данные. Автоматического изменения AD нет.

## Запуск

Требуются Python 3.11+ и Node.js 20+.

Терминал 1:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Терминал 2:

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173`. Документация API: `http://127.0.0.1:8000/docs`. При первом запуске backend автоматически создаст демонстрационное сканирование. Кнопка «Запустить анализ» обновляет результаты.

Для запуска на одном порту сначала выполните `npm run build` в `frontend`, затем запустите backend и откройте `http://127.0.0.1:8000`. После новой сборки frontend перезапустите backend.

## Подключение Active Directory

1. Убедитесь, что компьютер с backend видит контроллер домена по сети и порт LDAP/LDAPS открыт.
2. Создайте обычную доменную учётную запись с правом чтения каталога. Domain Admin не нужен.
3. Скопируйте `backend/.env.example` в `backend/.env` и заполните `LDAP_HOST`, `LDAP_BASE_DN`, `LDAP_USERNAME` и параметры порта/SSL. Пароль в файл не записывайте.
4. Перезапустите backend, откройте «Подключение», введите пароль сканера в скрытое поле и нажмите «Проверить соединение».
5. Выберите источник `Active Directory` и нажмите «Запустить анализ».

Пример для тестового стенда:

```env
LDAP_HOST=192.168.56.10
LDAP_PORT=389
LDAP_USE_SSL=false
LDAP_BASE_DN=DC=radar,DC=lab
LDAP_USERNAME=radar_scanner@radar.lab
```

Для реального окружения используйте LDAPS и проверку сертификата: `LDAP_PORT=636`, `LDAP_USE_SSL=true`, `LDAP_VALIDATE_CERT=true`. Отключать проверку сертификата допустимо только на изолированном тестовом стенде. Не добавляйте `backend/.env` в Git. Если интерфейс доступен по сети, защитите соединение браузера с backend через HTTPS.

## Что уже работает

- загрузка тестовых объектов или сбор пользователей и групп из AD через LDAP;
- прямое и вложенное членство в критических группах, в том числе Domain Admins, Enterprise Admins, Schema Admins, Administrators, Account Operators, Server Operators, Backup Operators, DNSAdmins;
- поиск неактивных, заблокированных и истёкших аккаунтов, бессрочных и старых паролей, ослабленных парольных требований;
- анализ сервисных и привилегированных аккаунтов;
- Risk Score 0–100, уровни Critical / High / Medium / Low, доказательства и рекомендации;
- базовая оценка доменной парольной политики: минимальная длина, сложность, порог блокировки;
- Dashboard с количеством неактивных аккаунтов и динамикой Score, поиск и фильтрация находок, карточки аккаунтов, CSV-экспорт;
- настройка порогов анализа в интерфейсе, настройка списка критических групп через `CRITICAL_GROUPS` в `.env`;
- хранение истории сканирований в SQLite и журналирование запусков.

Баллы правил: Critical 40, High 25, Medium 10, Low 5. Риск аккаунта и политики домена — сумма баллов с ограничением 100. AD Security Score = `100 − средний риск проверенных объектов` (аккаунты и домен, если политика доступна). Формула MVP простая и прозрачная; при промышленном использовании её потребуется согласовать с политикой компании.

## Известные ограничения MVP

- `lastLogonTimestamp` обновляется с задержкой, поэтому дата последнего входа приблизительная.
- Сервисный аккаунт определяется по SPN, префиксу имени или OU `Service Accounts`. В AD нет универсального поля «сервисный аккаунт».
- Интерактивный вход сервисного аккаунта не определяется надёжно по одному LDAP-атрибуту. Для такой проверки потребуются GPO или журналы входа; приложение не выдаёт предположение за подтверждённый факт.
- `memberOf` не включает основную группу пользователя (`primaryGroupID`), поэтому нетипичное членство через основную группу пока не учитывается.
- Fine-Grained Password Policies и фактическое право сервисных аккаунтов на интерактивный вход пока не анализируются.
- История в SQLite локальная, авторизация в веб-приложении пока отсутствует. Не публикуйте этот MVP в открытый интернет.
- ИИ-модули пока не подключены: для них нужны отдельный выбор модели и решение, какие данные AD можно передавать ей. Текущие причины и рекомендации формируются проверяемыми правилами.

## API

| Метод | Путь | Назначение |
|---|---|
| `POST` | `/api/scans` | Запуск `demo` или `ldap` сканирования |
| `POST` | `/api/connection/test` | Проверка LDAP и количества объектов |
| `GET` | `/api/dashboard` | Последняя сводка |
| `GET` | `/api/findings` | Находки, фильтр `severity` и `q` |
| `GET` | `/api/accounts` | Список аккаунтов |
| `GET` | `/api/accounts/{id}` | Карточка аккаунта |
| `GET` | `/api/scans` | История сканирований |
| `GET` | `/api/export/csv` | Выгрузка последнего отчёта |

cd backend

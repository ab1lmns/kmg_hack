# Identity Risk Analyzer

Рабочий MVP для анализа рисков тестового Microsoft Active Directory. React показывает результаты настоящего LDAP сканирования, FastAPI читает каталог под обычной учётной записью, детерминированные правила формируют находки и оценки, SQLite хранит историю и журнал действий, CSV выгружает отчёт. Приложение не исправляет AD автоматически.

## Архитектура

```text
React/Vite dashboard → FastAPI → LDAP collector (read only) → Account/Group snapshot
                                                     ↓
                           group paths → risk rules → scores → SQLite → API/CSV
```

Frontend находится в `frontend/src`, backend в `backend/app`. Исходный интерфейс сохранён; его страницы «Обзор», «Риски», «Аккаунты», «Политика домена» и «Подключение» используют API. Демо-источник остался доступен для автономной разработки, но при настроенном LDAP по умолчанию выбран Active Directory.

## Стенд и секреты

Тестовый домен — `infraradar.test`, контроллер — `INFRARADAR-DC01.infraradar.test`, Tailscale IP — `100.93.42.103`. LDAP доступен по `100.93.42.103:389`. Backend использует только `ir-ldap-reader@infraradar.test`, не Domain Administrator. LDAP-запросы ищут пользователей в `OU=InfraRadarLab,DC=infraradar,DC=test`, а группы читают во всём домене для разрешения вложенных путей. SSH алиасы `infraradar-host` и `infraradar-dc` нужны только для диагностики и подготовки лабораторных объектов.

Скопируйте `backend/.env.example` в `backend/.env` и задайте `LDAP_PASSWORD` в этом файле либо в переменной окружения процесса. `backend/.env` игнорируется Git; ограничьте его права (`chmod 600 backend/.env`). Не помещайте пароль в исходный код, README, тесты или HTTP-запросы из браузера. `/api/connection/status` сообщает лишь факт наличия секрета. Локальный стенд использует LDAP внутри зашифрованного Tailscale канала; для эксплуатации вне лаборатории настройте LDAPS или StartTLS и проверку сертификата.

## Запуск

Требуются Python 3.11+ и Node.js 20+. Из корня репозитория:

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

В другом терминале для разработки интерфейса:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://127.0.0.1:5173`. Для демонстрации на одном порту выполните `npm run build` в `frontend`, перезапустите backend и откройте `http://127.0.0.1:8000`. Оба сервера слушают только loopback; публичные порты не открываются. API доступен по `/docs`.

При первом запуске с настроенным LDAP Dashboard будет пуст до первого сканирования. Нажмите «Запустить анализ» с источником Active Directory либо выполните:

```bash
curl -X POST http://127.0.0.1:8000/api/scans \
  -H 'Content-Type: application/json' -d '{"source":"ldap"}'
```

Результат и история сохраняются в `backend/data/radar.db`; после перезапуска приложения последний scan остаётся доступен.

## Лабораторные данные

В `OU=InfraRadarLab` подготовлены 30 тестовых пользователей и 9 групп. Скрипт `scripts/Seed-DemoAD.ps1` можно повторно запустить через `python3 scripts/run_seed.py` с Mac. Он проверяет домен и OU, создаёт отсутствующие объекты, не сбрасывает пароли и не удаляет объекты. Все новые пользователи и группы находятся в тестовой OU; системные группы домена не изменяются.

Группе `IR-Lab-Admins` делегирован `GenericAll` **только на тестовую OU и её дочерние объекты**. Она включена в `CRITICAL_GROUPS`, поэтому цепочки вроде `ir-svc-backup → IR-Service-Ops → IR-Infrastructure → IR-Lab-Admins` отражают действительное право управления лабораторными объектами. Это не права Domain Admins и не доступ к остальному домену. Среди тестовых пользователей также есть прямые членства в системных административных группах, созданные ранее в стенде.

Для новых пользователей задаются случайные пароли, которые скрипт не выводит и не сохраняет. `lastLogonTimestamp` и `pwdLastSet` не подделываются. Поэтому сценарии старого входа и старого пароля проверяются синтетическими unit tests, а на настоящем AD появятся только после естественного старения данных.

## Правила и оценки

Реализованы 19 правил: отключённые, просроченные, заблокированные и неактивные учётные записи; Password Never Expires; старый пароль; PASSWORD_NOT_REQUIRED; прямые и вложенные критические группы; несколько ролей; отключённые и неактивные привилегированные аккаунты; сервисные аккаунты с бессрочным паролем, привилегиями, неактивностью или без владельца; минимальная длина пароля, сложность и порог блокировки домена. Каждый finding содержит причину, объяснение важности, evidence и рекомендацию. Приложение не исполняет рекомендации.

Прямое или вложенное членство в `Domain Admins`, `Enterprise Admins`, `Schema Admins` либо `Administrators` помечается Critical только при подтверждении группы в снимке AD. Делегирование `IR-Lab-Admins` относится к `OU=InfraRadarLab` и имеет High, а не выдаётся за Domain Admin. Область прав указана в карточке и evidence. Для сервисных аккаунтов статус интерактивного входа — `not_evaluated`: LDAP не сообщает результирующие права входа на каждом компьютере. Это требует анализа применённых политик разрешения и запрета входа на конкретных хостах.

`lastLogonTimestamp` приблизителен и обновляется с задержкой. Отсутствие записи о входе у нового пользователя не считается неактивностью: нужен возраст аккаунта выше порога. Сервисный аккаунт определяется по SPN, имени или OU; универсального флага в AD нет. Членство через `primaryGroupID` разрешается по SID группы.

Risk Score пользователя: худшая severity задаёт диапазон (`Low 10–29`, `Medium 30–59`, `High 60–79`, `Critical 80–100`), а остальные находки добавляют 30% своих баллов внутри этого диапазона. Нулевой score означает отсутствие находок. Поэтому несколько Medium правил сами по себе не создают Critical. Баллы правил: Low 5, Medium 10, High 25, Critical 40. Оценка политики домена — сумма её баллов с пределом 100. AD Security Score = `100 − средний Risk Score` проверенных аккаунтов и политики домена (если политика прочитана); **100 лучше, 0 хуже**. Пороги неактивности и возраста пароля настраиваются в интерфейсе; границы Risk Score задаются переменными `RISK_MEDIUM_THRESHOLD`, `RISK_HIGH_THRESHOLD`, `RISK_CRITICAL_THRESHOLD`, а критические группы — в `CRITICAL_GROUPS`.

## API и демонстрация

Основные endpoints: `GET /api/health`, `POST /api/connection/test`, `POST /api/scans`, `GET /api/scans`, `GET /api/dashboard`, `GET /api/accounts`, `GET /api/accounts/{id}`, `GET /api/findings`, `GET /api/groups`, `GET /api/export/csv`. Ни один endpoint не принимает LDAP пароль от браузера.

Для demo откройте Dashboard, проверьте источник Active Directory, запустите scan, откройте подтверждённый Critical аккаунт `ir-domainadmin` с прямым членством в `Domain Admins`, затем `ir-svc-backup` для вложенного пути к делегированной лабораторной OU. Покажите причины, объяснение, evidence и рекомендации, затем скачайте CSV. Фильтры страницы «Риски» позволяют выбрать severity, категорию, тип аккаунта, права, статус и строку поиска; сортировка — Risk Score, severity, username, дата активности или пароля. Второй scan показывает предыдущие и текущие Score/Critical/High, добавленные и исчезнувшие находки. CSV содержит категорию, Risk Score, причину, объяснение, evidence и рекомендацию. Подробный порядок: `docs/DEMO_SCRIPT.md`.

```bash
cd backend
.venv/bin/python -m unittest discover -s tests -v
RUN_LDAP_SMOKE=1 .venv/bin/python -m unittest discover -s tests -v
cd ../frontend && npm run build
```

Live LDAP smoke test включается только явной переменной `RUN_LDAP_SMOKE=1` и использует секрет из локального окружения, не из тестового кода. Он выполняет только чтение.

## Ограничения

- Нет автоматических изменений AD, анализа Security Event Log, Password Spray и Brute Force. Эти события нельзя достоверно вывести из одного LDAP снимка.
- Фактическое разрешение интерактивного входа сервисных аккаунтов помечено `not_evaluated`; Fine-Grained Password Policies не анализируются. Базовая доменная политика показывается полностью: длина, сложность, история, возраст и параметры блокировки.
- Нет авторизации веб-приложения: запускайте его локально, не публикуйте в интернет.
- SQLite хранит полные JSON снимки. Для PostgreSQL потребуется отдельная миграция слоя хранения.
- `IR-Lab-Admins` управляет только тестовой OU, а не доменом. Это явно помеченный лабораторный сценарий вложенных привилегий.
